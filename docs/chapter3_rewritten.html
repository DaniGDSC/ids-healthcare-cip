Section 3.1

Architectural overview

The system implements a seven-stage pipeline (modules 0–6) over the WUSTL-EHMS-2020 corpus (47 NetFlow-shaped features at ingest, reduced to 25 after preprocessing). Modules 0 and 1 run once per dataset and produce frozen artefacts; modules 2–6 are orchestrated end-to-end by run_all_modules.py on every build. The decomposition follows two principles: each module is a thin CLI shim over a tested package, and every stage's output is a file under results/ consumed by name by the next stage.

Section 3.2

Detection layer

The detection layer is a two-track cascade. Track A is a supervised classifier path trained on labelled attack data; Track B is a denoising-autoencoder novelty detector trained on benign-only data. The cascade fuses the two with a monotone-elevation rule that never lets the novelty signal lower the supervised decision.

Track A — three classifiers, one decision driver

Three classifiers are trained at M2: xgboost, random_forest, and decision_tree — registered in TRACK_A_MODELS at module2_detection/module2_train_models.py:202-221.

The name "XGBoost" in this work refers to scikit-learn's GradientBoostingClassifier wrapped as an XGBoost-equivalent surrogate. module2_detection/models/XGBoost.py:18 defines XGBoostDetector = GradientBoostingDetector, and the wrapper docstring (GradientBoosting.py:3-7) states the choice explicitly: "We use sklearn rather than the xgboost library." Performance is within a few F2 points of native xgboost on this corpus; the xgboost package is not a runtime dependency.

Only one Track A model — XGBoost — drives downstream decisions: PRIMARY_TRACK_A = "xgboost" at detection_engine/engine.py:90. Random Forest and Decision Tree exist solely to populate the analyst report's n_models_flagged vote count and its consensus = N / 4 string. They do not participate in the cascade fusion (engine docstring at engine.py:4-11).

Track B — DAE on benign-only data

The denoising autoencoder is trained on benign rows only. The mask is set once in module2_detection/dae_training.py:89-90: 

# module2_detection/dae_training.py:89-90
benign_mask = y_train == 0
X_benign    = X_train[benign_mask]

The fitted artefact reports "benign_train_samples": 8563 in results/models/dae_final_report.json:91. The architecture is documented in module2_detection/models/DAE.py:201-237: 

Input (n_features)
  → Winsorize + MinMax [0, 1] per-feature normalisation
  → Dropout(noise_rate)        # denoising corruption
  → Dense(encoder, relu)
  → Dense(bottleneck, relu)    # bottleneck strictly < n_features (assert)
  → Dense(decoder, relu)
  → Dense(n_features, sigmoid) # reconstruction in [0, 1]

Loss: MSE  ·  Optimiser: Adam(lr)  ·  default encoding_dims = [16, 8, 16]  ·  noise_rate = 0.1

The DAE input is a 26-dimensional augmented vector [raw_25_features || xgb_proba]. The list of Track A models whose probabilities are appended lives in common/dae_input.py:15 as TRACK_A_FOR_DAE = ("xgboost",) — the single source of truth shared with the inference engine. Changing the tuple requires retraining the DAE (the bottleneck width is fixed at fit time, and a stale artefact raises a width-mismatch ValueError at first inference call — engine.py:188-194).

Fusion — elevation-only by construction

The cascade fuses the supervised and novelty scores with a single line in detection_engine/engine.py:283: 

c_detect = np.clip(np.maximum(c_track_a, c_track_b), 0.0, 1.0)

The max operator makes the elevation-only property structurally true: the DAE can only raise c_detect above the XGBoost confidence, never lower it. A dedicated test — test_elevation_only_invariant at tests/test_detection_engine_cascade.py:142-159, added in Path B commit 2 — runs the engine with _force_full_dae=True over the full test split and asserts row-by-row that cascade.c_detect ≥ cascade.c_track_a holds. The comment above the fusion line documents the intent verbatim: "Fusion: DAE elevates, never suppresses Track A."

Compute-side gate (distinct from the decision boundary)

The engine also defines TAU_SKIP_DAE = 0.90 at engine.py:100. Rows where the XGBoost probability already exceeds 0.90 skip the DAE forward pass and receive c_track_b = 0. This is a compute optimisation, not a decision boundary; it is held strictly distinct from each Track A model's calibrated decision threshold (loaded from get_track_a_thresholds(), typically well below 0.9). The cascade test in tests/test_detection_engine_cascade.py:88-139 validates that gated rows have c_detect == c_track_a and that the gated cascade never exceeds the full-DAE result by more than a 0.20 budget per row.

Feature sanitisation

DetectionEngine._sanitise(X) (engine.py:138-150) replaces any NaN / Inf in the input batch with 0.0 and casts the matrix to float32. This is the minimal guard that lets a malformed row pass through without crashing GradientBoostingClassifier (which raises on NaN). The identifier in the source comment is OOD-05; richer data-quality strategies (median-impute with per-feature quality flags, multiplier-based confidence discounts) are not implemented and are deferred to future work.

Section 3.3

Risk-scoring layer

Module 3 produces a per-alert composite risk score in [0, 1] and maps it to one of five tiers. Two formulas coexist in the codebase — a paper-frozen linear weighted sum (v1, the default this chapter documents) and a Sprint-4 architectural improvement (v2, opt-in) — but the live risk_scores.npz artefact and every downstream consumer use v1.

The composite formula (v1, default)

R = w1·Cdetect + w2·Dcrit + w3·Sdata + w4·Apatient
where {w1, w2, w3, w4} = {0.40, 0.25, 0.15, 0.20}
clipped to [0, 1]

The constants live in module3_risk_scoring/config.py:17 as a literal dict; no training path mutates them. They are policy parameters, not learned weights — the chapter's contribution is the surfacing decision the formula encodes, not a claim of optimality. The implementation is two lines in module3_risk_scoring/composition.py:63-69.

The four inputs

InputRangeSourceAnchor
C_detect [0, 1] Cascaded fusion max(c_track_a, c_track_b) from the detection engine detection_engine/engine.py:283
D_crit [0, 1] Attack-category → CIA risk lookup, scaled by a single default device tier (vital_monitoring = 0.8). See note below. module3_risk_scoring/components.py:47-59
S_data [0, 1] (1.0 · bio_active + 0.4 · net_active) / 1.4, where each *_active is the fraction of features with |value| > 0.01 module3_risk_scoring/components.py:63-107
A_patient (D_clinical_tier in code) [0, 1] Fraction of biometric features with |value| > SIGMA_THRESHOLD = 1.5 (NEWS2 "moderate deviation") module3_risk_scoring/components.py:111-121
naming note — D_crit
As implemented, D_crit is not a per-row device criticality. The function compute_d_crit(attack_cats) ignores the per-row device tier and uses DEFAULT_DEVICE_TIER = "vital_monitoring" for all samples. The corpus has no per-row device-class label, so the value varies only by attack category at the assumed default tier. Extending to per-row device tier (which the DEVICE_TIERS table at config.py:122-128 already supports) is left as future work.

Five tiers, not four

Tier mapping is performed by assign_risk_levels(R) at composition.py:118-164. The boundary table at config.py:35-40 defines four thresholds and an implicit fifth tier:

Range of RTierSurface to operator?
R ≥ 0.80CRITICALescalate
0.60 ≤ R < 0.80HIGHsurface — actionable
0.40 ≤ R < 0.60MEDIUMsurface — informational
0.30 ≤ R < 0.40LOWaudit-log only
R < 0.30NORMALno action — routine logging

NORMAL is a deliberate fifth tier. Without it, the v1 formula assigned ~85% of test rows to LOW because a vital-monitoring device with PHI data crosses R ≈ 0.21 from the context components alone. The NORMAL band, combined with the detection gate below, lifts operational precision from 0.125 to 0.686 on the test split without moving the surfaced-tier (MEDIUM+) precision / recall that the RQ1 paper depends on (config.py:23-34 comment).

The detection gate

A second mechanism, the detection gate MIN_DETECTION_GATE = 0.02 at config.py:49, acts on C_detect rather than on R. Any row whose detection signal is below 0.02 is forced to NORMAL regardless of how high its context-driven R climbs. This prevents the "context floor" failure mode: an idle but critical device with PHI data cannot trigger an alert from context alone.

A note on the v2 formula

Sprint 4 introduced a multiplicative architectural alternative: R = Cdetect × (1 + α·Dcrit + β·Sdata + γ·Apatient) with the detection gate as a Layer-1 zero. The full derivation is in docs/formula_v2_rationale.md. v2 is opt-in via --formula-version v2 on the M3 CLI; this chapter documents v1 because the live artefact and every downstream consumer use v1.

Per-device adjustments live in the dashboard adapter

Module 3's batch path produces a static base risk score. Per-device adaptations — patchability, baseline quarantine for newly-enrolled devices, maintenance-window suppression, similar-event learning — live in src/risk_scorer.py and are invoked at per-alert granularity from the dashboard adapter at module6_evaluation/_src_adapter.py:35-39. This is a two-path design: the M3 batch is what the offline metrics measure; the dashboard adapter is what an operator sees.

Safety floor — "Invariant 2"

The chapter's primary safety-floor anchor is src/risk_scorer.py:142-147: 

# Safety floor: CRITICAL + unpatchable devices must ALWAYS surface.
# The IDS is the ONLY compensating control for unpatchable devices.
if criticality == "CRITICAL" and not patchable:
    should_surface = True

A second, related, queue-ordering floor lives in the dashboard's module6_evaluation/triage_helpers.py:floor_elevated — it adds a non-dismissable badge when a CRITICAL alert has d_crit ≥ 0.5 or d_clinical_tier ≥ 0.4. Both sites are tested. The chapter treats the first as Invariant 2 proper, and the second as its dashboard-surface counterpart.

Section 3.4

Explanation layer

Module 4 produces three artefacts per alert: a SHAP attribution against XGBoost, a DAE per-feature reconstruction-error vector, and a 3-layer Minimum Viable Explanation (MVE). The three are joined and rendered through three role-specific surfaces in the dashboard.

SHAP attribution — XGBoost only

The gating constant SHAP_MODELS = ("xgboost",) at module4_explanations/config.py:55 restricts TreeSHAP to the production decision driver. The implementation uses shap.TreeExplainer(clf) at compute.py:97. Random Forest and Decision Tree are excluded explicitly via SKIP_SHAP_MODELS (config.py:59-60) — they contribute only the consensus vote string in the analyst report.

The three-layer MVE

The MVE shape is documented as a dataclass in src/data_models.py:62-87:

LayerThemeKeysWord budget
Layer 1WHY anomalousbaseline_behavior, deviation_description, confidence_indicator≤ 60
Layer 2CLINICAL SEVERITY (Impact)affected_system, patient_care_impact, phi_exposure, severity_label, severity_rationale≤ 50
Layer 3RECOMMENDED ACTIONimmediate_action, clinical_constraint, escalation_path, timeframe≤ 60

Total budget is ≤ 150 words across all three layers — the MVEOutput.total_word_count property at data_models.py:104-115 sums word counts across all twelve fields. The cap is enforced at generation time (see Word-budget enforcement below).

Mode A (LLM) and Mode B (rule-based) with explicit fallback

The provider chain is encoded directly in src/mve_generator.py:1175-1199: 

# Provider chain: A1 (OpenAI) → A2 (Anthropic) → B (rule-based).
# Each LLM helper returns None on missing key, uninstalled SDK,
# failed call, or invalid response.
provider_used = "rule_based"
if force_rule_based:
    mve = None
else:
    mve = _generate_llm_openai(...)
    if mve is not None: provider_used = "openai"
    else:
        mve = _generate_llm_anthropic(...)
        if mve is not None: provider_used = "anthropic"
if mve is None:
    mve = _generate_rule_based(...)

The chosen provider is recorded on MVEOutput.provider ∈ {"openai", "anthropic", "rule_based"} so downstream consumers can attribute every MVE. A batch tripwire MVE_LLM_FAIL_STREAK_MAX = 5 forces rule-based for the remainder of a batch once five consecutive LLM calls fail (module5_responses/__init__.py:29).

Degradation badge

Path B commit 4 added a dashboard-side visual signal at module6_evaluation/module6_app.py:_render_provider_badge. When the renderer sees alert["mve"]["provider"] == "rule_based", it surfaces "⚠ Rule-based explanation (LLM unavailable) — verify alert details independently before acting" as a Streamlit warning at the top of all three role views (analyst, clinician, administrator). LLM-sourced MVEs get a quieter caption naming the provider. The helper is unit-tested in tests/test_provider_badge.py.

Word-budget enforcement (hard cap)

The 150-word total cap is instructed in the LLM system prompt and enforced at runtime by a check immediately after the provider chain returns (mve_generator.py:1281-1297, added in Path B commit 3): 

if provider_used != "rule_based" and mve.total_word_count > 150:
    logger.warning("MVE word-budget exceeded (%d > 150) ...")
    mve = _generate_rule_based(...)         # budget-safe by construction
    provider_used = "rule_based"

An over-budget LLM response is rejected and replaced with the deterministic rule-based template. The contract is tested by tests/test_mve_word_budget_hard_cap.py (an LLM mock returning a ~200-word output triggers fallback; an in-budget mock is preserved).

Stakeholder adaptation

The router at module4_explanations/nlg.py:184-241 dispatches on a string role. Internal keys are analyst, clinician, and administrator; the user-facing labels in the user study are different. The cross-walk is documented in docs/rq3_tier_surfacing_appendix.md:36-38 and reproduced here:

Code keyUser-facing roleProxies
analystIT GeneralistSOC analyst, IT support
clinicianNurse ManagerBedside Clinician, Nurse Practitioner
administratorBiomed EngineerBiomedical Engineering, Service Line Owner, Charge Nurse

Each role's view differs in format and framing, not in underlying severity. The analyst view surfaces SHAP top-5 features and a waterfall chart; the clinician view renders a plain-language NLG summary with a biometric safety note; the administrator view emits aggregate severity + risk score + action flag. The dataclass schema for the alert record is role-independent — assertion enforced by test_inv9_alert_record_keys_role_independent at tests/test_step13_cross_role_consistency.py:116.

PHI redaction at the prompt boundary

Path B commit 1 added a defence-in-depth layer in _build_user_prompt (src/mve_generator.py:867-878): every dynamic payload (raw_alert, device_context, baseline, user_context) is wrapped with sanitize_for_log before interpolation into the prompt. The sanitiser at src/__init__.py:5-31 pattern-replaces SSN, MRN, patient-name, and date-of-birth substrings with [*-REDACTED] sentinels. The contract is tested by three assertions in tests/test_mve_prompt_phi.py: (i) no PHI string survives into the prompt; (ii) operational non-PHI tokens round-trip; (iii) at least one redaction sentinel appears, proving the sanitiser ran.

A parallel allow-list filter (_filter_for_llm, reading configs/llm_data_flow.yaml) is being added upstream of the prompt builder; the two defences are complementary and independent.

Faithfulness gate (offline)

The relationship between SHAP attribution and the clinician-facing narrative is measured offline by the narrative_faithfulness metric at module4_explanations/phase0_metrics.py:81-148: the probability that the clinician narrative's top-1 category matches the SHAP top-1 category, joined per sample_index. The CI gate tools/faithfulness_gate.py:71 enforces a floor of 0.85; the current value on the test split is 0.9674 (results/phase0_baseline.json).

Three additional explanation-faithfulness validators live in module4_explanations/validation.py: validate_consistency (SHAP rank vs sklearn feature_importances_), validate_perturbation (F1 drop when top-N features are masked), and validate_cross_model (Spearman rho and top-5 overlap across the three Track A models).

Section 3.5

Response & audit layer

Module 5 selects a per-alert response, runs a clinical-safety check, and writes a hash-chained, ECDSA-P256-signed audit log. The whole layer is non-executing by design: no code path calls a real blocking, isolation, or quarantine primitive. The ActionExecutor is explicitly simulated at module5_responses/executor.py:7-8: "Simulated executor: logs actions to audit trail instead of real changes."

Response selection — two orthogonal axes

Two configuration tables drive selection. The first is TIER_POLICIES at module5_responses/config.py:149-205 — keyed on the risk tier and carrying a priority (1–5), a default action list, a maximum response window, and a recommendation flag. The second is ATTACK_ROUTING at module5_responses/config.py:214-249 — keyed on attack category and carrying primary / secondary / tertiary roles plus attack-specific add-actions.

There is no "L1 / L2 / specialist" tier; the routing structure is two-dimensional. A single role can receive a CRITICAL Spoofing alert via ATTACK_ROUTING["Spoofing"].primary and a HIGH Data Alteration alert via ATTACK_ROUTING["Data Alteration"].primary — the tier governs urgency and action set, the attack category governs which role is on the hook.

"auto_execute_recommended" — naming matters

The tier policy carries an auto_execute_recommended flag (renamed from auto_execute in Path B commit 6) for CRITICAL and HIGH tiers. The name change is load-bearing for the chapter's no-auto-execution claim: the field is an advisory only; nothing in the codebase reads it to drive a real action. The simulated executor records the recommendation as auto_executed_simulated in the audit record, again making the simulation-vs-execution distinction visible to any reviewer reading the chain. Backwards compatibility with pre-rename artefacts is preserved by Pydantic AliasChoices at common/alert_response_schema.py:127.

Two sub-stages, one package

The orchestrator runs Module 5 as two scripts:

  • M5 — module5_responses.py builds the per-alert record set (520 records on the test split, 320 on demo) and writes the audit chain.
  • M5b — module5_pipeline.py drives the PolicyEngine + clinical_safety_check + FeedbackLoop; this is where the closed-loop re-baselining lives.

Both scripts share the module5_responses package; the split keeps the per-alert write path (M5) separate from the policy / feedback workflow (M5b).

Hash-chained, ECDSA-signed audit chain

AuditLogger.log() at module5_responses/audit/logger.py:147-198 builds each record in five steps:

  1. optional reviewer block (only for dashboard-triggered records);
  2. record["prev_hash"] = self.prev_hash (genesis = "0" * 64);
  3. record["integrity_hash"] = sha256(canonical_json(record)).hexdigest();
  4. if signing: signature = base64(ecdsa_sign(canonical_json(record), SHA256));
  5. self.prev_hash = record["integrity_hash"]; append as a JSONL line.

The signature algorithm is SIGNATURE_ALG = "ECDSA_P256_SHA256" (audit/logger.py:20). Verification at audit/verify.py:32-181 walks every record on replay, re-computes the hash, validates the chain, and checks the signature. The chain is tamper-evident, not tamper-resistant — an attacker with write access to the JSONL file can rewrite history; the chain detects it but does not prevent it.

Two distinct hash fields, two distinct purposes

The audit chain in audit_log.jsonl uses integrity_hash (64-char ECDSA-signed chain). The batch audit records in audit_trail.json use record_fingerprint (16-char per-row content checksum) — renamed in Path B commit 5 from a previously-overloaded integrity_hash. The rename eliminates a name collision that previously made it ambiguous whether a record had been signed or only fingerprinted.

Three audit sinks, one fan-out

Every operator action produces three writes: online_interactions.jsonl (buffered, optimised for high-frequency render events; not the trust anchor), audit_trail.jsonl (SHA-256 hash-chained, no signature), and audit_log.jsonl (the signed chain). The dashboard's HardenedAuditLogger is the single authority for routing operator interactions through this fan-out.

Two caveats on the audit schema

Reviewer attribution is populated only on dashboard-triggered records (acknowledge / escalate / dismiss). Batch records (machine-generated classifications) carry no reviewer block by construction — there is no human in the loop at write time.

The simulated_outcome sub-record on each batch entry is a research artefact, not an operational signal. It is computed against ground truth at log time and would not exist in a real deployment — the field's purpose is to let RQ3 measure false-positive-isolation rate without re-running the pipeline.

One related property: elevation-only fusion

The detection layer's fusion rule (§3.2) is not numbered as a design invariant, but it shares the same shape: a property that is structurally true in code and now has a dedicated regression test. tests/test_detection_engine_cascade.py:test_elevation_only_invariant asserts row-by-row over the full test split that cascade.c_detect ≥ cascade.c_track_a holds. This test was added in Path B commit 2 and is the chapter's anchor for "the cascade only elevates, never suppresses."

The reserved invariant numbers (1, 4, 8) are not gaps left by omission — they are slots reserved for future safety properties whose definitions are not yet stable. Treating the numbering as deliberate keeps the existing six anchored to their tests without forcing artificial renumbering when new invariants land.
