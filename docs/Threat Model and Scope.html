1 · Adversary model

The pipeline is hardened against a network-side adversary with black-box knowledge of the model. The threat model is documented in docs/rq1_threat_model_scope.md and enforced in code through a small number of named TM-IDs plus a wider set of unnamed defenses.

Adversary assumptions

AxisIn-scope adversary
KnowledgeMay know the architecture; no white-box access to model weights or training-data ordering.
CapabilityCan issue arbitrary NetFlow-shaped traffic from the clinical network or external sources routed through the span port.
Adaptivitynot assessed Reported metrics assume non-adaptive attackers.
PersistenceSustained probing against TM-04 jitter is acknowledged out-of-scope (averaging defeats jitter; rate-limit assumed external).

3 · Deliberately out of scope

Four classes of threat / capability the codebase makes no claim against. Each item is named with an OOS-* identifier and anchored to a quotable comment or doc reference. The four classes correspond to the four cards below.

class · detection
Detection surface
What network features cannot see. Payload content, endpoint-only activity, encrypted exfiltration with normal flow shape, novel attack families, insider misuse, physical-layer attacks. 6 items (OOS-D1 → D6).
class · adversary
Adversary capability
Adaptive evasion, white-box weight access, sustained probe-and-average against TM-04 jitter, flow-shape perturbation evasion. 4 items (OOS-A1 → A4).
class · crypto
Cryptographic boundary
Anything past a compromised audit signing key, malicious authoring at training time, bugs in restored model code, hostile-controlled pickle bytes, auto-bootstrap key on shell- compromised host. 5 items (OOS-K1 → K5).
class · evaluation
Evaluation scope
Response-action correctness (RQ1 does not claim it), raw detector recall on critical devices (gated by safety floor), specificity↔FNR_critical trade-off, per-class detection on the 4 placeholder categories. 4 items (OOS-E1 → E4).

trust boundary
The system trusts three things: (a) the audit signing private key, (b) the signed dataset baseline in module0_analysis/dataset_integrity.json, (c) the host running Module 0 ingest. Compromise of any of these defeats every downstream defense in the table.

Deployment checklist

  1. Network: span port / TAP into the IoMT VLAN producing stable NetFlow-shape records with the 47-feature ingest schema.
  2. Keys: HSM- or KMS-provisioned ECDSA P-256 PEM, exported through IOMT_AUDIT_SIGNING_KEY. Do not ship the auto-bootstrap key into production.
  3. Storage: append-only filesystem (or equivalent WORM) for results/reports/audit_log.jsonl and the rotation archive.
  4. Identity: external SSO/SAML auth bootstraps participant_id + sim_role in the Module 6 session — codebase has no login flow.
  5. Egress: allow HTTPS to OpenAI / Anthropic only if you want LLM-enhanced MVE; otherwise the rule-based fallback is offline-safe.
  6. Rate-limit: firewall / NAC / WAF must enforce per-source throttling against the IDS endpoint — TM-04 jitter alone does not stop sustained probing.
  7. Drift response: operator owns the retraining trigger when Module 4 drift detection flags shift; codebase does not auto-retrain.
  8. Tenancy: one process + workspace + signing key + audit log per hospital. Reuse across sites is not supported.
  9. Compliance: HIPAA Safe Harbor is covered at ingest; GDPR / IEC 62443 obligations need separate evidence outside this codebase.
single weakest link
Rate-limiting and key management are both delegated to the deployment layer. If either is absent, the named TM-04 defense and the OOS-K5 caveat collapse — the threat model held in code no longer matches reality on the host.
