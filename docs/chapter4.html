Section 4.2

The Train/Inference Symmetry Problem

Status summary — post-execution. Cascade / OOF / F2-tuning code unchanged (already correct). The §5.2.3 ablation citation is now corrected to results/dae_raw_benign_only_ablation.json via D1 reframe #8; the "F2 across all detectors" phrasing is clarified (Track-A only; DAE 95th-percentile) via D1 reframe #10. 23 cascade + OOF tests PASS.
Problem
Track B (DAE) is trained on [raw_features ‖ Track_A_probas] (dae_training.py:78-105). If the Track A probabilities used at training time were resubstitution probas (the same model that saw the labels predicting on those same rows), the DAE would learn against a distribution it never sees at inference, and the F2-tuned threshold would calibrate against memorised ~0 / ~1 probas — explicit warning at module2_train_models.py:285-295: "WUSTL-EHMS data return probas pinned to ~0 / ~1 on training rows".
Solution
OOF probas via sklearn.model_selection.cross_val_predict on a freshly cloned SMOTE+classifier pipeline — module2_detection/models/_base_detector.py:156-163 and module2_train_models.py:298-306; CV is StratifiedKFold(n_splits=5, shuffle=True, random_state=run_seed). OOF probas persisted to results/models/{name}_oof_proba.npy (module2_train_models.py:370-373); DAE training loads them via _load_oof_probas (dae_training.py:52-75) and column-stacks onto benign rows — the DAE never sees resubstitution probas. F2-optimal threshold per Track-A model: module2_detection/models/_threshold.py:29-69 calls precision_recall_curve, applies vectorised F-beta, returns thresholds[argmax(fbeta)]; default beta = 2.0; fallback 0.5 on degenerate input. Thresholds invoked against OOF probas, not training probas. Inference cascade: detection_engine/engine.py:168-199 (build_augmented) and :201-293 (predict), with width assertion at engine.py:185-194.
Verify
tests/test_detection_engine_cascade.py — 5 tests; tests/test_module2_dae_training.py — 6 tests; tests/test_module2_train_models.py — 12 tests; ran together → 23 PASSED in 7.70 s. No test directly asserts the OOF non-leakage property — the guarantee rests on the contract of sklearn.cross_val_predict.

Defending Against Data-Quality Attacks

Status summary — post-execution. The EA-06 defence has been restored. Problem
A crafted feature vector with NaN/Inf or extreme-rate missingness could (a) crash downstream models (GradientBoostingClassifier raises on NaN — engine.py:140-141) or, more dangerously, (b) be coerced to a "harmless" form and silently produce a low risk score, hiding the attack. The outline frames this as the EA-06 NaN-injection attack and claims a four-state quality flag drives an upward score adjustment so worse data ⇒ higher risk, never silencing.
Solution
What exists: a single static helper DetectionEngine._sanitise at detection_engine/engine.py:137-150 that replaces NaN/Inf with 0.0 on a logger.warning, called at engine.py:177, 226. Docstring labels it the "OOD-05 guard", not EA-06. Behaviour is silent coercion, not upward elevation. A NaN-biometrics row becomes a zero-vector before reaching XGBoost — which typically produces a low proba and a lower risk. The closest analogue to BENIGN_MEDIAN is artifacts/feature_baselines.json, produced by tools/build_feature_baselines.py; it records median / iqr_low / iqr_high / p05 / p95 / unit / decimal_places / is_biometric / n_benign per feature — n_benign = 8,563 (the train benign count), not 9,990. This file is consumed only by Module 4's narrative explainer (module4_explanations/feature_groups.py:78-90), not by the scoring path. What does NOT exist: no DataQuality class (whole-repo grep class DataQuality = 0 hits); no IMPUTED_NAN / DEGRADED / FAILED states for input quality; no ×1.20 elevation multiplier for input quality (the only 1.20 in source is a device-tier multiplier at src/risk_scorer.py:35, unrelated); no ≥ 0.95 FAILED floor.
